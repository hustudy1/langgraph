# llm_wiki 작성 시 AI가 유의해야 할 사항

이 문서는 llm_wiki 문서를 **생성·갱신하는 AI**가 지켜야 할 작성 원칙이다.
각 원칙은 AI 공식 문서에 근거하며, 출처는 `03_REFERENCES.md`에 정리되어 있다.

## 1. 짧고 구체적으로 쓴다 (준수율의 문제)

근거: Claude Code 공식 문서 "How Claude remembers your project"

- 세션 시작 시 자동으로 불러오는 **핵심 AI 지시 파일은 파일당 200줄 이하**를 목표로 한다.
  지시가 길어질수록 컨텍스트를 낭비하고 AI의 준수율이 떨어질 수 있기 때문이다.
- 이 권장은 프로젝트의 일반 `README.md`, 설계·API 문서, 소스 코드, 테스트 파일에는 적용하지 않는다.
  `HANDOVER.md`처럼 매 세션 읽는 문서는 현재 상태를 중심으로 유지하고 오래된 기록을 아카이브한다.
- 검증 가능한 수준으로 구체적으로 쓴다.
  - 나쁨: "코드를 잘 정리해라" / 좋음: "들여쓰기는 스페이스 2칸을 사용한다"
  - 나쁨: "변경사항을 테스트해라" / 좋음: "커밋 전에 `npm test`를 실행한다"
- 마크다운 헤더와 불릿으로 구조화한다. AI도 사람처럼 정리된 섹션을 더 잘 따라간다.

## 2. 명확하고 직접적으로 쓴다

근거: Anthropic 공식 문서 "Prompting best practices"

- AI를 "똑똑하지만 우리 팀의 관례를 전혀 모르는 신입 직원"으로 간주하고 쓴다.
- **골든 룰**: 맥락이 없는 동료에게 이 문서를 보여줬을 때 그대로 따라 할 수 있으면 AI도 따라 할 수 있다.
- 순서나 완전성이 중요한 절차는 번호 목록으로 쓴다.
- 하지 말라는 것("~하지 마라")보다 해야 할 것("~해라")을 명시하는 편이 효과적이다.
- 규칙에는 **이유(왜)** 를 함께 적는다. AI는 이유를 알면 상황에 맞게 일반화한다.
  - 나쁨: "절대 말줄임표를 쓰지 마라"
  - 좋음: "출력이 TTS로 읽히므로 발음할 수 없는 말줄임표를 쓰지 마라"

## 3. 예시를 포함한다

근거: Anthropic 공식 문서 "Prompting best practices" (few-shot prompting)

- 형식·톤·구조를 지정할 때는 규칙 설명보다 잘 만든 예시가 더 확실하다 (공식 문서 권장: 3~5개).
- 예시는 실제 사용 사례와 가깝게, 서로 다르게(엣지 케이스 포함) 만든다.
- 좋은 예/나쁜 예를 대비해서 보여준다.

## 4. 모순을 만들지 않는다

근거: Claude Code 공식 문서 "How Claude remembers your project"

- 두 규칙이 충돌하면 AI는 임의로 하나를 고른다. 문서를 갱신할 때마다 기존 규칙과 충돌하는지 확인한다.
- 낡은 규칙은 남겨두지 말고 삭제하거나 갱신한다.
- 코드나 git 히스토리에서 파생 가능한 내용(파일 구조, 과거 수정 내역)은 중복 기록하지 않는다.
  중복 기록은 코드가 바뀌는 순간 모순의 원천이 된다.

## 5. 환각(hallucination)을 구조적으로 방지한다

근거: Anthropic 공식 문서 "Reduce hallucinations"

- 문서에 **"모르면 모른다고 쓸 권한"을 명시적으로 부여한다**. 이것만으로 거짓 정보가 크게 줄어든다.
  (본 가이드에서는 `[UNKNOWN]` / `[UNVERIFIED]` 태그로 구현)
- 검증이 중요한 사실 주장에는 근거(인용, 출처)를 붙이게 하고,
  **근거를 찾지 못한 주장은 철회**하게 한다.
- 계산, 추론, 비기술적 판단처럼 공식 문서가 없는 질문은 출처를 억지로 만들지 않고
  전제, 계산 과정, 판단 기준을 밝히게 한다.
- 제공된 문서·코드에 기반해 답하게 하고, 일반 지식으로 빈칸을 메우지 않게 한다.
- 주의: 이 기법들은 환각을 크게 줄이지만 **완전히 제거하지는 못한다**.
  중요한 결정에 쓰이는 정보는 반드시 사람이 최종 검증한다.

## 6. 어떤 AI 도구에서도 읽히게 쓴다 (이식성)

근거: AGENTS.md 표준(agents.md), llms.txt 제안(llmstxt.org)

- **표준 마크다운**이 사실상 모든 LLM 도구가 읽는 공통 포맷이다. 특정 도구 전용 문법
  (frontmatter 확장, 독점 태그 등)에 핵심 내용을 담지 않는다.
- AGENTS.md는 OpenAI Codex, Google Jules, Cursor, GitHub Copilot 등 다수 에이전트가 읽는
  표준 마크다운 개방형 관례이고, Claude Code는 CLAUDE.md를 읽는다.
  llm_wiki를 단일 원본(source of truth)으로 두고 두 파일이 llm_wiki를 참조(import/링크)하게
  하면 중복 없이 모든 도구를 지원할 수 있다. (출처: https://agents.md/, 확인일: 2026-07-07)
- llms.txt 제안도 "LLM이 가장 널리, 쉽게 이해하는 포맷은 마크다운"임을 전제로 하며,
  간결·명확한 언어와 설명 없는 전문용어 회피를 권장한다. (출처: https://llmstxt.org/, 확인일: 2026-07-07)

## 7. 시점 독립적으로 쓴다

- 상대 시간 표현("어제", "최근", "지금") 대신 절대 날짜(YYYY-MM-DD)를 쓴다.
  AI 세션마다 "오늘"이 다르기 때문이다.
- 외부 정보에는 확인일을 남긴다: `(출처: <URL>, 확인일: 2026-07-06)`
- AI의 학습 데이터에는 지식 마감일(knowledge cutoff)이 있다. 문서에 기록된 버전·URL·API가
  현재도 유효한지는 읽는 쪽 AI가 재확인해야 함을 전제로 쓴다.

## 8. 갱신 시 체크리스트

llm_wiki 문서를 만들거나 고칠 때마다 확인한다:

- [ ] 처음 보는 AI가 이 문서만 읽고 이해할 수 있는가? (맥락 의존 표현 없음)
- [ ] 모든 규칙이 검증 가능한 수준으로 구체적인가?
- [ ] 기존 규칙과 모순되는 내용이 없는가?
- [ ] 검증이 중요한 사실 주장에 출처가 붙어 있는가?
- [ ] 출처가 없는 계산·판단에는 전제와 추론 과정이 명시되어 있는가?
- [ ] 불확실한 내용에 `[UNKNOWN]` / `[UNVERIFIED]` 표기가 되어 있는가?
- [ ] 상대 날짜가 아닌 절대 날짜를 썼는가?
- [ ] 비밀값, 개인 정보, 운영 리소스 정보가 그대로 노출되지 않았는가?
- [ ] `HANDOVER.md` 기록 기준에 맞는 내용만 남겼는가?
- [ ] 최근 작업의 현재 상태·검증 결과·Git 상태가 `HANDOVER.md`와 일치하는가?
- [ ] `commit`과 `push`를 각각 실행하기 전에 사용자 승인을 받도록 명시했는가?
- [ ] 작업 로그가 10개를 넘으면 오래된 기록을 아카이브했는가?
- [ ] 가이드 버전과 최종 갱신일이 현재 내용과 맞는가?
- [ ] 세션 시작 시 자동 로드되는 핵심 AI 지시 파일이 200줄 이하인가? (일반 프로젝트 문서와 코드는 제외)

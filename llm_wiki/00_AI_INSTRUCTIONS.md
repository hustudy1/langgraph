# AI 기본 지시사항 (llm_wiki Core Instructions)

이 문서는 이 프로젝트에서 작업하는 AI를 위한 **저장소 공통 지침**이다.
시스템·개발자·사용자 지시, 도구 권한과 충돌하면 더 높은 지시와 기술적 제약을 따른다.
매 세션 시작 시 이 문서와 이 폴더의 `HANDOVER.md`를 먼저 읽고 작업을 시작한다.
`HANDOVER.md`가 없고 구현·수정 작업이며 쓰기 권한이 있으면
`02_HANDOVER_TEMPLATE.md`를 복사해 만든 뒤 코드와 설정 파일에서 확인 가능한 항목을 채운다.
단순 읽기·분석·리뷰 요청에서는 새 파일을 만들지 않는다.
모르는 항목은 `[UNKNOWN]`으로 남긴다.

## Core Directives (English summary for cross-model compatibility)

1. Write everything so that ANY AI model can understand it: standard Markdown only, no tool-specific syntax.
2. Maintain `llm_wiki/HANDOVER.md` like a work handover: record what was done, current state, and next steps accurately.
3. If you do not know something, explicitly mark it as `[UNKNOWN]`. Never present a guess as a fact.
4. Use the strongest available evidence: official docs for technical/vendor claims, repository evidence for project-specific claims, and explicit assumptions/calculations for reasoning tasks.
5. Important factual claims need a verifiable, trustworthy source. If no authoritative source exists, explain the assumptions and reasoning instead of inventing one.
6. Fact-check important claims before responding. For complex answers that need follow-up judgment, suggest exactly one likely next question.

## 6대 원칙

### 1. 모든 AI 모델이 이해할 수 있게 작성한다
- 표준 마크다운만 사용한다. 특정 도구(Claude Code, Cursor 등) 전용 문법에 의존하지 않는다.
- 약어·내부 코드네임은 첫 사용 시 반드시 정의한다.
- "어제", "지난주" 같은 상대 날짜 금지. 항상 절대 날짜(예: 2026-07-06)로 쓴다.
- 파일 경로는 프로젝트 루트 기준 상대 경로로 쓴다 (예: `src/api/handlers/user.ts`).
- 이전 대화의 맥락을 아는 사람만 이해할 수 있는 표현을 쓰지 않는다.
  기준: **이 프로젝트를 처음 보는 AI가 이 문서만 읽고 작업을 이어갈 수 있는가?**

### 2. 인수인계하듯 작업 내용을 공유한다
- 작업을 시작하기 전에 `llm_wiki/HANDOVER.md`를 읽는다.
- 구현·수정 작업의 의미 있는 단위가 끝날 때마다 `llm_wiki/HANDOVER.md`를 갱신한다:
  무엇을 했는지, 왜 그렇게 결정했는지, 현재 상태, 미해결 문제, 다음에 할 일.
- 실패한 시도도 기록한다. 다음 AI가 같은 실수를 반복하지 않게 하는 것이 목적이다.
- `HANDOVER.md`는 다음 경우에 갱신한다:
  아키텍처, API, 데이터 모델, 배포 방식, 실행/검증 방법이 바뀐 경우;
  다음 작업자가 알아야 할 실패·제약·미해결 문제가 생긴 경우;
  장기 작업을 중단하거나 인수인계해야 하는 경우.
- 단순 오타 수정, 포맷팅, 작은 내부 리팩터링처럼 다음 작업자에게 새 맥락을 주지 않는 변경은
  `HANDOVER.md`에 기록하지 않아도 된다.

### 3. 모르는 것은 모른다고 표기한다
- 확신할 수 없는 내용은 문장 앞에 `[UNKNOWN]` 태그를 붙인다.
- 부분적으로만 확인된 내용은 `[UNVERIFIED]` 태그를 붙이고 무엇이 미확인인지 명시한다.
- 추측이 필요한 경우 "추측:"이라고 명시하고 근거를 함께 쓴다.
- 모른다고 답하는 것은 실패가 아니다. 틀린 정보를 사실처럼 전달하는 것이 실패다.

### 4. 주제에 맞는 가장 강한 근거를 사용한다
- 라이브러리, API, 프레임워크, 보안, 운영 절차에 관한 답변은 해당 프로젝트나 벤더의 공식 문서를 우선 근거로 한다.
- 프로젝트 내부 상태에 관한 답변은 저장소의 코드, 설정 파일, 테스트, 이슈, 커밋 같은 직접 근거를 우선 사용한다.
- 계산, 추론, 비기술적 판단처럼 공식 문서가 없는 질문은 전제, 계산 과정, 판단 기준을 명시한다.
- 기억(학습 데이터)에 의존한 버전·시그니처·설정값은 공식 문서로 확인하기 전에는 `[UNVERIFIED]`로 취급한다.
- 공식 문서와 블로그/커뮤니티 글이 충돌하면 공식 문서를 따른다.
- 공식 문서가 없는 주제에 출처를 억지로 만들지 않는다.

### 5. 근거와 출처를 제시한다
- 외부 사실, API/라이브러리 사용법, 보안/운영 판단처럼 검증이 중요한 주장에는
  출처(공식 문서 URL, 저장소 내 파일 경로, 커밋 해시 등)를 함께 쓴다.
- 출처가 필요한데 찾지 못한 주장은 삭제하거나 `[UNKNOWN]`으로 표기한다.
- 계산이나 판단으로 답하는 경우에는 출처 대신 사용한 전제와 추론 과정을 짧게 밝힌다.
- 출처 표기 형식: `(출처: <URL 또는 파일 경로>, 확인일: YYYY-MM-DD)`

### 6. 중요한 주장을 팩트체크한 뒤 답변한다
- 답변을 내보내기 전에 각 주장에 대해 스스로 검증한다:
  "이 주장의 근거는 무엇인가? 근거를 제시할 수 있는가?"
- 근거를 제시할 수 없는 중요한 사실 주장은 답변에서 제거하거나 `[UNKNOWN]`으로 표기한다.
- 검증을 실행하지 못했거나 외부 상태를 확인하지 못했으면 그 범위와 이유를 밝힌다.
- 간단한 결과 보고나 단답에는 예상 질문을 붙이지 않는다.
- 조사, 설계, 인수인계, 선택지 비교처럼 복잡하거나 후속 판단이 필요한 답변에는
  사용자가 이어서 물을 가능성이 높은 예상 질문을 답변 마지막에 정확히 1개 제시한다.

## 행동 규칙

- 사용자가 `llm_wiki 참고해서 앞으로 프로젝트 진행해줘` 또는 같은 의미의 요청을 하면,
  이를 프로젝트 전체 작업에 이 가이드를 적용하라는 표준 시작 요청으로 해석한다.
- 표준 시작 요청을 받은 뒤에는 문서 읽기, `HANDOVER.md` 준비·갱신, 코드 조사, 구현,
  검증과 결과 보고를 이 가이드에 따라 스스로 수행한다. 사용자가 각 절차를 따로 요청하게 하지 않는다.
- 표준 시작 요청을 받으면 현재 작업 디렉터리와 Git 루트를 확인해 프로젝트 루트를 결정하고,
  Claude Code와 Codex를 번갈아 사용해도 되도록 다음 연결 파일을 모두 생성하거나 보완한다:
  - 프로젝트 루트 `CLAUDE.md`에 `@llm_wiki/00_AI_INSTRUCTIONS.md`를 추가한다.
  - 프로젝트 루트 `AGENTS.md`에 작업 전 `llm_wiki/README.md`,
    `llm_wiki/00_AI_INSTRUCTIONS.md`, `llm_wiki/01_WRITING_GUIDELINES.md`와
    `llm_wiki/HANDOVER.md`를 읽고 따르라는 지시를 추가한다.
- 연결 파일이 이미 있으면 기존 내용을 보존하고, 동일한 연결 또는 지시가 없을 때만 추가한다.
  파일을 쓸 권한이 없거나 프로젝트 루트를 안전하게 결정할 수 없으면 임의 위치에 만들지 말고 보고한다.
- 자동 연결의 공식 지원 범위는 로컬 프로젝트 파일을 읽고 쓸 수 있는 Claude Code와 Codex이다.
  다른 AI에서는 해당 도구가 지원하는 프로젝트 지시 파일을 확인할 수 있을 때만 연결한다.
  일반 웹 대화처럼 로컬 파일 접근 권한이 없으면 자동 연결을 시도하지 않는다.
- 같은 대화와 프로젝트에서는 이후 작업마다 `llm_wiki` 적용 여부를 다시 묻지 않는다.
  새 세션에서 규칙 파일이 자동으로 로드되지 않았다면 사용자의 표준 시작 요청이나 도구별 연결 파일이 필요하다.
- 사용자가 `llm_wiki/`를 참고하라고 하면, 해당 폴더의 `README.md`, `00_AI_INSTRUCTIONS.md`,
  `01_WRITING_GUIDELINES.md`, `HANDOVER.md`(없으면 `02_HANDOVER_TEMPLATE.md`)를 먼저 읽고 작업한다.
- 구현·수정 작업을 완료할 때마다 `HANDOVER.md`의 현재 상태, 검증 결과,
  미해결 문제와 다음 할 일이 실제 상태와 맞는지 확인하고 필요한 부분을 갱신한다.
- 요청이 조금 불명확해도 아래 조건을 모두 만족하면 질문하지 말고 진행한다:
  변경 범위가 작다; 쉽게 되돌릴 수 있다; 데이터 삭제, 비용 발생, 배포, 보안/개인정보 영향이 없다;
  기존 코드나 문서에서 합리적인 방향을 확인할 수 있다.
- 진행 후에는 어떤 가정으로 처리했는지 결과 보고에 짧게 적는다.
- 아래 경우에는 사용자 확인을 요청한다:
  요구사항 해석에 따라 결과물이 크게 달라질 수 있는 경우;
  삭제, 초기화, 운영 반영, 비용 발생, 보안/개인정보 영향이 있는 경우;
  도구나 실행 환경이 명시적 승인을 요구하는 경우.
- 사용자가 "중간 확인 없이 진행", "알아서 끝까지 진행"이라고 명시하면,
  고위험 작업과 도구 승인 필요 상황을 제외하고 질문하지 말고 완료까지 진행한다.
- 하지 않은 작업을 했다고 말하지 않는다. 테스트가 실패했으면 실패했다고 결과와 함께 보고한다.
- 문서를 수정할 때는 낡은 내용을 남겨두지 않는다. 갱신하거나 삭제한다.
- 이 문서와 `llm_wiki/` 내 다른 문서가 충돌하면 이 문서(`00_AI_INSTRUCTIONS.md`)가 우선한다.

## 코딩 작업 안전 규칙

- 저장소라면 작업 전 `git status`를 확인하고, 사용자가 만든 변경을 되돌리지 않는다.
- Git 저장소에서 작업이 완료되면 `git diff`와 `git status`를 확인하고 변경 파일과
  권장 커밋 메시지를 사용자에게 보고한다.
- `git add`와 `git commit`은 실행 직전에 사용자에게 물어보고 명시적으로 승인받은 경우에만 수행한다.
- 원격 `push`도 실행 직전에 별도로 물어보고 명시적으로 승인받은 경우에만 수행한다.
- 사용자가 앞선 요청에서 일반적으로 Git 기록을 원한다고 밝혔거나 프로젝트 규칙에 자동 커밋이
  적혀 있어도, 현재 작업의 `commit`과 `push`에 대한 확인을 생략하지 않는다.
- 승인을 받은 뒤에도 작업 전부터 있던 사용자 변경, 별개 작업, 비밀값, 생성물은 현재 작업 커밋에 혼합하지 않는다.
- 브랜치 생성·삭제와 히스토리 재작성도 사용자의 명시적 승인 없이 수행하지 않는다.
- `git reset --hard`, 강제 push, 대량 삭제, 운영 DB/결제/배포/클라우드 리소스 변경은
  사용자의 명시적 승인 없이 수행하지 않는다.
- 새 구현 전에 README, 설정 파일, lock 파일, 테스트, 주변 코드를 먼저 확인한다.
- 기존 패턴, 프레임워크, helper API, 테스트 방식을 우선 사용한다.
- 새 의존성을 추가해야 하면 이유와 영향을 설명하고, 프로젝트 관례 또는 사용자 승인을 따른다.
- 변경 후 가능한 가장 좁은 테스트부터 실행한다. 실행하지 못한 테스트는 이유를 보고한다.
- API 키, 토큰, 쿠키, 개인 정보, `.env` 값은 답변이나 문서에 그대로 노출하지 않는다.
- 로그나 오류 메시지에 비밀값이 보이면 마스킹해서 보고한다.
